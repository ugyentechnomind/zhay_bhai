# Modules & extension points

This is a scaffold, not a finished product - the pieces below are the seams
meant for teammates to build on without fighting the existing structure.

## 1. Excuse tones

`packages/shared/src/types.ts` defines `ExcuseTone` and `EXCUSE_TONE_LABELS`.
Both the dashboard and the extension read this list to build their tone
picker - add a new tone by adding one entry there, nothing else needs to
change to make it selectable.

The actual wording is generated by `apps/web/src/lib/anthropic.ts` -
`generateExcuse()`. If you want per-tone prompt tweaks (e.g. a "sick" excuse
should never mention symptoms in detail), that's the function to extend.

## 2. Excuse generation provider

`generateExcuse()` in `apps/web/src/lib/anthropic.ts` is the single call site
used by `excuseService.ts`. To swap providers (a different model, a
template-based fallback with no API cost, etc.), keep the same signature:

```ts
function generateExcuse(input: {
  eventTitle: string;
  organizerName: string | null;
  tone: ExcuseTone;
  senderFirstName: string;
}): Promise<{ subject: string; body: string }>
```

and swap the implementation `excuseService.createExcuseForEvent()` calls.

## 3. Sending provider

`sendGmail()` in `apps/web/src/lib/google.ts` is the only place that sends
mail. It assumes the user's own Gmail via their OAuth grant. A teammate adding
Outlook/Microsoft 365 support would add a parallel `sendOutlookMail()` and a
`connected_accounts.provider` column to pick between them in
`excuseService.sendExcuse()`.

## 4. Calendar provider

`fetchCalendarWindow()` in `apps/web/src/lib/google.ts` is the only place that
reads events. Same shape as above applies for a second calendar source
(Outlook Calendar, etc.) - it would need to normalize into the same
`calendar_events` row shape (`syncCalendarForUser()` in `excuseService.ts`).

## 5. The "Bunk" button injection (extension content script)

`extension/src/content-script.ts` is the fragile part of this project by
nature: Google Calendar has no documented extension point for its RSVP row,
so the script finds it by the `aria-label` ("Yes"/"No"/"Maybe") on the RSVP
buttons - more stable than class names, but still liable to break when Google
changes their markup.

Two things a teammate can meaningfully harden here:

- **Event ID resolution** (`resolveEventId()`): currently decodes the `eid=`
  query param off a "more details" link, falling back to fuzzy-matching the
  popover's accessible name against the locally cached event list. If neither
  works, the button shows an error toast telling the user to use the popup
  instead - that fallback path should stay, but the resolution itself could
  use a second strategy (e.g. matching by start time in addition to title).
- **A second injection target**: RSVP buttons also show up in Gmail's
  calendar invite emails, not just calendar.google.com. Extending
  `content_scripts.matches` in `extension/manifest.json` to include
  `https://mail.google.com/*` and adjusting the selectors would extend Zhay
  Bhai AI there too - worth its own PR since the Gmail DOM is different.

If this script ever silently stops finding the RSVP row, the popup (which
talks to the same `/api/extension/bunk` endpoint through
`extension/src/lib/api.ts`) still works - that's the reliability fallback by
design, not an oversight.

## 6. New API routes

Route handlers under `apps/web/src/app/api/` all follow the same shape:
resolve the acting user via `resolveRequestUserId()` (works for both the
cookie-based web session and the extension's bearer token), then call into
`excuseService.ts` or `google.ts`. Keep new routes on that pattern so they
work from both the dashboard and the extension for free.
